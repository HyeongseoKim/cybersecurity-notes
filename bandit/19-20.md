# Bandit — Level 19 → 20

- **Date:** 2026-09-14
- **Time spent:** about 20 minutes
- **Note:** Written right after solving.

## The goal, in my own words

The password for the next level was in `/etc/bandit_pass/bandit20`, which only
bandit20 can read. I was logged in as bandit19, so I could not read it directly.
The home directory held a special program, `bandit20-do`, that let me run a
command as bandit20.

## What I tried first

I listed the home directory to see what was there:

```bash
ls -la
```

Most files were owned by root, but one file, `bandit20-do`, stood out. Its
permissions had an `s` where I expected an `x`:

```
-rwsr-x--- 1 bandit20 bandit19 ... bandit20-do
```

I had not seen `s` in a permission string before, so I looked into what it meant.

## Where I got stuck

When I checked level 19, one file had an owner permission changed from `x` to
`s`. I had not seen `s` before, so I looked it up. At first I thought it meant
"give my permission to someone else." That was not right. The program does not
give my permission away — when another user runs it, they borrow the owner's
identity for as long as the program runs.

## What actually worked

Running the program with no arguments printed its usage:

```bash
./bandit20-do
```

```
Run a command as another user.
  Example: ./bandit20-do whoami
```

To check that it really changed my identity, I compared `whoami` run two ways:

```bash
whoami
./bandit20-do whoami
```

The first printed `bandit19` (me). The second printed `bandit20`. Same person
running it, but the system treated the second one as bandit20. That is what the
`s` bit does: while the program runs, it uses the owner's identity, not mine.

So I used it to read the password file that only bandit20 can read:

```bash
./bandit20-do cat /etc/bandit_pass/bandit20
```

## New to me

| Command / concept | What it does | Where else I'd use it |
|---|---|---|
| `s` in permissions (setuid) | While the program runs, it uses the file owner's identity instead of the user who ran it. It can lend much more power than it looks, so it must be used carefully. | Checking a system for setuid files that should not have the bit |
| owner vs root | The owner is whoever a file belongs to (different per file); root is the one system administrator | ___ |
| running a program with no arguments | Often prints its usage, which is a quick way to learn how to use it | ___ |
| `whoami` | Prints which user I am right now | ___ |

## One thing I still don't fully understand

`bandit20-do` is owned by bandit20, so it only lends bandit20's identity. I read
that if a program with the `s` bit is owned by root and has a bug, a normal user
could use it to gain root. I do not yet understand how that actually happens.
