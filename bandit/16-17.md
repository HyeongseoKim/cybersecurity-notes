# Bandit — Level 16 → 17

- **Date:** 2026-09-10
- **Time spent:** not recorded
- **Note:** I solved this level on 2026-09-08 and wrote it up two days later.

## The goal, in my own words

In most earlier levels, the password was in a file, and I used it to log in as
the next user. Level 16 was different: I had to connect to an open port on the
same machine, and what I received was a private key, not a password.

## What I tried first

The level gave me a range of ports (31000-32000). Checking every port by hand
would have taken too long, so I first looked for a command that could check a
whole range at once. I found `nmap`, but my first attempt failed:

```bash
nmap -p -sV 31000-32000 localhost
```

```
Error #486: Your port specifications are illegal.
Example of proper form: "-100,200-1024,T:3000-4000,U:60000-"
QUITTING!
```

I put `-sV` right after `-p`, so nmap tried to read `-sV` as the list of ports.
`-sV` is not a valid port range, so nmap stopped with an error instead of
scanning. Changing the order fixed it.

## Where I got stuck

I found a file that started with 'BEGIN OPENSSH PRIVATE KEY', followed by
hundreds of characters. I did not know how to use it. In most earlier levels,
each level gave me a 32-character password, so I expected the same thing again.
Level 13 had already given me a private key, but I had forgotten how to use it,
so I was confused again.

I also could not save the key where I first tried. I ran `nano ~/bandit17.key`
and got:

```
Unable to create directory /home/bandit16/...
```

`ls -la ~` showed why: my home directory is owned by `root`, so as bandit16 I
only get `r-x` on it. I can read it and enter it, but I cannot write to it.
That is why I saved the key under `/tmp` instead.

## What actually worked

```bash
nmap -sV -p 31000-32000 localhost
```

```
PORT       STATE SERVICE     VERSION
31XXX/tcp  open  echo
31XXX/tcp  open  ssl/echo
31XXX/tcp  open  echo
31XXX/tcp  open  ssl/unknown
31XXX/tcp  open  echo
```

`-sV` was the important part. Without it, nmap only tells me which ports are
open, and every open port looks the same — just a number. With `-sV`, nmap
talks to each open port and reports what service is behind it.

Two ports used ssl, so at first they both looked possible. But an echo service
only sends back what you send it, so `ssl/echo` could not give me anything new.
Only one port was `unknown`, which means nmap could not match it to a normal
service. That was the port I needed.

Because the port used ssl, I did not use `nc`. I remembered that level 15 had
the same problem, so I used `openssl s_client` instead.

```bash
openssl s_client -connect localhost:31XXX -quiet
```

```
depth=0 CN=SnakeOil
verify error:num=18:self-signed certificate
```

The certificate did not verify because the server signed its own certificate
instead of getting it from a trusted authority. On a practice server that is
fine, but on a real site this warning would mean something is wrong.

I saved the private key that came back into a file under `/tmp`, and used it
with `ssh -i`:

```bash
ssh -i /tmp/bandit17.key bandit17@localhost -p 2220
```

Port scanning is only acceptable here because the Bandit server is a practice
environment that invites it. I would not run this against a machine I do not own.

## New to me

| Command / concept | What it does | Where else I'd use it |
|---|---|---|
| options that take a value vs options that do not | `-p` needs a value after it, but `-sV` can stand alone. If I put another option right after `-p`, `-p` swallows it as its value. | Every Linux command, not just nmap |
| `nmap -p` | Chooses which ports to scan. It always needs a value. | |
| `nmap -sV` | Talks to each open port and reports what service is behind it. It does not take a value. | |
| `echo` service | Only sends back what you send it, so it cannot give you anything new | |
| `openssl s_client` | A subcommand of `openssl`. It connects to a port that speaks SSL, which `nc` cannot do. | |
| `openssl s_client -quiet` | Hides the session and certificate details. The certificate verification result still showed, so it does not silence everything. | |
| self-signed certificate | A certificate the server signed itself, instead of a trusted authority signing it | The browser warning "this connection is not secure" |
| private key | A file that proves who I am, used instead of a password | |
| `-----BEGIN ... END-----` | A label that says what kind of data is inside the block | HTTPS certificates use the same format |
| `ssh -i` | Points ssh at the key file I want to use as my identity | |
| `r` and `x` on a directory | They are not the same. I could not run `ls /tmp`, but I could still open `/tmp/bandit17.key` because I knew the exact path. | |
| file permissions like `-rw-------` | Only the owner can read or write the file | ssh refuses to use a key file that other users can read |
